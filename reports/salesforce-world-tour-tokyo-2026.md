## 2. 全体サマリー

4つのセッションから、AI活用は「入れる」段階から「安全につないで、定着させ、評価し続ける」段階に移っていると感じました。要点は次の3つです。

1. **業務の窓口はSlack、土台はSalesforce**：Slackは人・エージェント・各種ツールを集める「work operating system」を掲げています。SalesforceはMCP ServerやHXL、Agent Identityにより、ClaudeやChatGPTなど外部AIからも権限を守って使える基盤になりつつあります。
2. **成果を分けるのは導入より定着**：JTBはアンバサダー方式、SCSKは実装から改善までの伴走体制、Salesforce社内では「共通認識×当事者意識」を定着の鍵としていました。継続利用が20%にとどまった失敗事例も紹介されています。
3. **開発者の仕事は「書く」から「任せて責任を持つ」へ**：実行はAIに任せ、人は指示・設計・接続・統制を担います。答えが合っていても過程が間違うことがあるため、評価の仕組みを先に作ることが重視されていました。

## 3. セッション別の内容

### 3-1. 【2-B-4】Agentic Enterpriseの扉をひらく！対話を組織の資産に変えたJTBの選択とSlackforceが導くSalesforceの未来

Slackは「仕事とは対話そのもの」という考えで、会話を組織の資産に変える場を目指しています。JTBはその考えで営業の属人化を解消した事例を紹介しました。

**内容の要点（Slack CPO）**

- 「新しいSlack：your work operating system」として、すべてのPeople・すべてのAgents・あらゆるPlatform・ひとつのAI Teammateを一か所に集め、Multiplayer AIにとって最高の場所にする。
- プレゼンなどは過程に過ぎず、仕事の本体は対話である。エージェントとの会話もコンテクストとして蓄積され、組織全体が成長していく。
- 問題解決の初期に「なんとかなる」ものはほとんど役に立たない。苛立ちや障害にこそ価値があり、努力の成果は後半で大きくなる。価値が一番伸びるところを探すべき。

**内容の要点（JTB 大塚 代表取締役）**

- 課題：ナレッジが個人に留まり広がらない（暗黙知・属人化）。背景に、顧客ニーズの多様化、退職者や法人営業未経験者の増加、働き方改革による提案準備時間の減少がある。
- 2つの手：ナレッジワークを「勝ち筋ナレッジベースHub」、Slackを「コミュニケーションHub」として導入。ビジョンは「暗黙知を、集合知に。」。
- 「対話の置き場所の変換」というカルチャー変革を起こし、「相談先が一本化され、判断が速くなった」という顧客評価を得た。
- 日常の運用：#おめでとうチャンネルで受注を称え、Salesforce for Slackが案件情報を自動で投稿する。「リアク字」で負荷なく反応が集まる。以前は営業担当がSales Cloudに潜って案件を探す必要があった。
- 定着の壁はガバナンス・ユーザー・データ・AIの4つ。各拠点のアンバサダーが推進し、現場でユースケースを生み、非公開chの作成権限など権限設計も整えた。
- AIの効きどころ：Slack（日々8,000人が投稿するフロー情報）、ナレッジワーク（勝ち筋）、Salesforce（案件情報・セールスレポート）をSlackbotスキルの知識源にし、営業社員の質問に回答・示唆を返す。経験の浅い領域でもAIの力で「専門性」を持てる。
- SlackbotはSlack自体のアップデートではなく、さまざまなアイテムを接続することで成長させる。ひとつのAIエージェントでは全社員に対応できない。

**紹介された新機能**

| 機能 | 概要 |
| --- | --- |
| Surfaces（Slackforce新機能） | Slackbotに頼むだけで、散らばったビジネスデータをダッシュボード形式のワークスペースにしてリアルタイムで可視化。Salesforceのレコード変更もbotから可能 |
| Slackbot in channels | チャンネルにAIとチームメイトが同居し、会話がナレッジとして蓄積される |
| 動画・スライド作成 | チームメイトと一緒に修正できる |
| 音声会話 | 直感的でフレンドリーな会話ができる |
| Slackのコード機能（Codey） | Codeyをメンションして問い合わせの調査を依頼すると、専用チャンネルが作られ関係者が参加。コードの差分や変更履歴を確認でき、AIとのやりとりも後から追える |
| Slack Frontlineライセンス | 提供開始の紹介（詳細は未確認） |

**印象に残った事例・数字**

- JTBでは日々8,000人がSlackに投稿し、そのフロー情報がそのままAIの知識源になっている。
- 「相談先が一本化され、判断が速くなった」という顧客評価。

**所感（下書き）**

AI活用の成否は、ツールより「対話をどこに置くか」で決まるという点が印象的でした。JTBでは会話をSlackに集めたことが、そのままSlackbotの知識源になっています。自分も質問や相談をオープンな場で行うことが、組織のナレッジづくりにつながると感じました。

### 3-2. 【2-B-5】SCSKと考える、AI時代のSalesforce活用：AIforceを支えるPlatformの進化

Salesforceの強みであるデータと認証基盤を、ClaudeやChatGPTなど外部のAIからも安全に使えるようにする新機能が中心でした。前提として、AIには判断基準と「AIハーネス」が必要だと説明されました。

**内容の要点**

- 一般的なAI基盤は5層：Apps＆インターフェイス／安全性・評価・ガードレール／ツール利用・統合（MCP）／データ＆ナレッジ（RAG）／基盤モデル（LLM、マルチモーダル）。
- Enterprise AI Harness：データ・業務機能・管理機能を備えたSalesforceの企業向けAI実行基盤。Trusted Models／Context／Agency／Action／Governance／Securityの6要素と、AIの登録・ポリシー・稼働状況・コストを一元管理するAI Control Planeからなる。
- デモの流れ：Claude Codeの開発プラグインで仕様書からSalesforceアプリ一式を作る→Builder CentralでAIと会話しながら修正・公開→HXLでSlack・Claude・ChatGPTから同じ体験を提供。「仕様から作り、言葉で直し、どこでも同じ見た目で使う」。
- 使えるからといってすぐ使うのではなく、これまでのセキュリティ設計をきちんと守ることが前提。
- SCSKの支援体制：「Salesforce・AIは導入するだけでは成果につながらない」。活用構想から継続改善までを支援するCXMOと、現場で実装・定着・改善を担うFDEが一気通貫で伴走する。

**紹介された新機能**

| 機能 | 提供状況 | 概要 |
| --- | --- | --- |
| Headless Experience Layer（HXL） | Beta | 業務の意図を一度定義すれば、Web・モバイル・Slackbotなど各チャネル向けにUIを自動変換。Salesforceのセキュリティ・ガバナンスを継承 |
| Salesforce MCP Server（旧Headless 360 MCP Server） | Beta | エージェントがSalesforceの機能を使う窓口は4つだけ：Discover（検索）・Describe（詳細取得）・Read（読み取り）・Dispatch（実行） |
| Headless Toolkit | 事前定義済みエージェントスキル・Setup with Agentforce・Agentforce Vibes 2.0・Agentforce LabsはGA | API・MCPツール・スキル・CLIで、Claude CodeやCodexなど使い慣れた開発エージェントからSalesforceの設定・保守・開発ができる |
| Salesforce Multi-Framework | ― | ReactやAngularでSalesforce上の開発ができる。Expert FrameworkがAI生成コードを検証・最適化し、認証とガバナンスも適用 |
| Salesforce Microfrontend | ― | 既存のWebアプリ（Reactなど）をセキュアなiframeでSalesforce画面に組み込み、双方向にデータ連携。重複開発を減らせる |
| Agent Identity／Agent Access | ― | Salesforce外のAIエージェントにIDを付与。利用者とAIの双方に許可された操作だけを実行し、問題時はそのエージェントだけ無効化できる |
| 管理業務のノーコード一元化 | ビルド・デプロイはBeta（2026年9月）、管理・有効化は一般提供、最適化・セキュリティは今後 | アイデアからアプリ作成、ALM・DevOps、Sandbox・本番組織の設定、不要項目の整理や設定改善まで |

**印象に残った事例・数字**

- Agent Accessの例：利用者は商談を参照・削除できても、AIエージェントには参照だけを許す、といった制御ができる。
- SCSKはFDE人材を2027年に100名規模にする計画。

**所感（下書き）**

外部のAIからSalesforceを操作できる範囲が広がるほど、「誰の代わりに、何をしてよいか」を決める権限設計が重要になると感じました。普段学んでいるClaude CodeがSalesforce開発の入口として紹介されており、AI駆動開発とSalesforceの知識がつながることも実感しました。

### 3-3. 【C-8】“便利ツール”のその先のAI活用～現場に浸透させた実践ステップ～

AIをチームに定着させるには「共通認識×当事者意識」が必要だという結論でした。Salesforce社内の成功事例と失敗事例を比べて説明されました。

**内容の要点**

- 問題提起：「個人作業は便利になったのに、チームの仕事は変わらない」。
- Customer Zero：製品を開発した組織自身が最初のユーザーになり、その体験で改善や価値を検証する戦略。JPKT Customer Zero Teamは「We are ALL Customer Zero」を掲げ、製品・ユースケース情報（全社向けSlackチャンネル）、経験できる環境（コンテストやワークショップ）、語れるコンテンツの3本柱で活動している。
- 4R：人とAIエージェントが共に働くために、Redesign（業務の再設計）・Reskill（AIへの指示や任せる業務を見極める力）・Redeploy（人を戦略・判断・創造の業務へ）・Rebalance（役割バランスの継続調整）を行う。
- AI活用の組織レイヤーモデル：全社共通の業務はCXO、チームで標準化できる業務はチーム長、個人タスクは従業員個人が責任を持つ。本セッションは主にチーム層の話。
- AI活用のゴールに向けて、次の順で業務を分解する。各ステップでチームの認識をそろえ、すべて自分たちの手で進める。
    1. 全業務を棚卸しする
    2. ペインポイントを特定する
    3. AIに任せるべき業務を特定する
    4. ユースケース案を出す（インパクト×スピードで優先順位）
    5. AIを選定し、業務とツールの責任者を決めて運用設計へ

**成功事例と失敗事例**

- 成功（インサイドセールスチーム）：顧客ごとの活動準備（企業調査・メール作成・架電準備など）に膨大な時間がかかり、属人化・ゼロからの作業・情報の分散が詰まりだった。上の5ステップをチームで議論して決め、個人の困り事を「チームで取り組む課題」に変えた。四半期プランニングのインサイト提示（手動起動）や、メール文面とカレンダーの自動送信（自動起動）を実装した。
- 失敗（ある営業組織）：勉強会でAIを提供し、各自が判断して使うことを想定した。結果は継続使用が全体の20%のみで、実行数も上がらず、AIの育成も行われなかった。企画側が「想定した」使い方を案内しただけで現場の優先度と結びつかず、改善責任の所在も不明瞭だった。

| 観点 | 成功事例 | 失敗事例 |
| --- | --- | --- |
| 課題設定 | 現場が業務の課題を抽出 | 現場の課題との接続が不足 |
| 共通認識 | 議論で優先課題を合意 | 目的の共有が不足 |
| 運用・改善 | 業務設計の責任者を明確に立てた | オーナーが不在 |
| 結果 | 継続的な運用から成果が発生 | 定着せず不発に終わる |

失敗からの教訓として、導入時の合意に加え、現場の声を受けて業務とシステムを改善する「担当」と「機会」が必要だとされました。その場として、前半で業務整理、後半でAI活用施策を検討するワークショップも紹介されました。

**明日からできるチームでの第一歩**

- 共通認識をそろえる：繰り返し負担を感じる業務を選ぶ→工程・担当・受け渡しを書き出す→時間や手戻りが生じる箇所と理由を話し合う。
- 当事者意識をもつ：改善したい課題、成功の基準、運用・改善の責任者、次の見直し時期を決める。
- まずは1つの業務から小さく試す。

**印象に残った事例・数字**

- 成功事例では、AI活用の意欲が94%、会話品質が97%向上。
- 失敗事例では、継続して使っているメンバーは全体の2割ほど。

**所感（下書き）**

同じ社内でも、ツールを配るだけでは2割しか使われなかったという失敗事例が特に参考になりました。AIの性能より、「どの詰まりを解くのか」を現場と合意し、責任者を決めることが定着を左右すると学びました。配属後は、まず自分のチームの業務の流れを知るところから始めたいです。

### 3-4. 開発者が創る Agentic Enterprise～AIforceとAIで変わる開発体験～

AIに実行を任せ、開発者は成果に責任を持つという役割の変化を、家具ECのデモで示したセッションです。作る→評価する→直す→リリースする、の反復をSalesforce上でどう回すかが示されました。

**内容の要点**

- 開発者の役割は4つに広がる：DIRECT（ゴールを決めAIを導く）、ARCHITECT（知能・ロジック・データ・ツールの連携を設計）、CONNECT（企業のコンテキストと機能を結ぶ）、GOVERN（境界を決め信頼と制御を作り込む）。
- デモの題材は架空の家具販売企業「AW Shop」。好みのテイストで探し、商品カードで比べて注文するエージェントを作り、同じウィジェット定義をWebとSlackの両方で使う（HXL）。
- AI向けのメソドロジーは、計画と設計→構築と統合→テストと実験→デプロイと利用→実行→拡張とモニタリングの反復。スピード、柔軟性、反復が不可欠。
- Testing Center：会話の台本ではなく「目的と行動条件」を定義すると、模擬ユーザーがエージェントと会話し、会話全体を自動で採点する。観点は「目的を達成したか」「必要なアクションを呼んだか」「独自の基準を満たしたか」。
- 修正の管理：Lifecycle CenterでWork Itemを作り、指定したSandboxでAgent Scriptを修正、GitHubのWork Item専用ブランチにコミットする。PipelineでDevelopment→Integration→UAT→Productionへ、Test gateを通しながら昇格させる。
- 自律型エージェント：アーキテクト・ビルダー・レビュアー・リリースの4役が、設計からデプロイまでを自動またはオンデマンドで実行する。人はポリシーを設定し、エージェント群をオーケストレーションする（「1人＝オペレーター1人」から「1人＝無限のオペレーター」へ）。
- まとめは「委任（AIに任せる単位はコードから成果へ）」「役割（指示・設計・接続・統制）」「反復（実装・評価・変更と配備の反復で速さと品質を両立）」の3つ。

**印象に残った事例・数字**

- 「エージェントは完走したが、過程に赤信号」：目的達成の評価は5/5でPassだったが、商品詳細を取得するアクションを呼ばず、検索結果の紹介文だけで素材を回答していたためアクション評価はFail。回答の素材表記も商品データとずれていた。
- 独自基準「AW最終案内の完全性」では3点でFail（合格は4点以上）。注文確定後の最後の応答に受付番号がなかった。毎回確かめたいことを評価基準として残せる。
- Lifecycle CenterのAnalytics（Dev Preview）では、AIが書いたコードの採用行数や採用率、削減時間の推計を追える（デモ画面では採用率 64%、削減時間 992時間など）。

**所感（下書き）**

最終的な答えが正しくても、必要な手順を飛ばしていることがある、というデモが最も印象に残りました。AI駆動開発では、何を期待するかを評価基準として先に言葉にしておくことが、品質を保つ鍵だと感じました。自分の学習でも、テスト観点を先に書く習慣を取り入れたいです。
